
# 项目规约：Zpython（Django + Channels + WebRTC + Taro 前端）

本规约用于把“要什么（spec）”明确成可验收的约束，并指导实现/评审/回归。

## 规约速查 (Quick Reference)

- 红线: 单文件 < 400 行 (R1) | 禁止提交任何密钥/口令/私钥 (R19) | WebSocket 消息类型与 HTTP API 变更先询问 (R4)
- 询问: 变更 URL/接口返回结构/WS 协议字段 (R4) | 引入/升级 pip/npm 依赖 (R5) | 修改异步/并发模型 (R12)
- 规范: Python `snake_case`/`UpperCamelCase` (R13) | UTF-8 文本约定 (R26) | 资源用 `with`/上下文管理器 (R15)
- 流程: 任何需求先 `requirements.md`/`design.md`/`tasks.md` 并逐段确认 (R32, R33)
- 分层: 视图/消费者只做适配；业务逻辑集中在 `zapp/services/` (R6, R21)

## 角色与背景

- 角色: Python/Django/Channels 全栈工程实践专家（兼顾 Linux 线上部署与 Windows 本地开发）。
- 背景: 本仓库包含 Django 网站、Channels WebSocket 信令、WebRTC 房间管理、自建 STUN 服务，以及 Taro（React + TS）前端工程。

## 技术栈

- 后端: Python + Django（见 [manage.py](manage.py)、[zproject/settings.py](zproject/settings.py)）。
- 实时: Django Channels + Daphne（见 [zapp/consumers.py](zapp/consumers.py)、[zproject/asgi.py](zproject/asgi.py)）。
- WebRTC: 浏览器侧 RTCPeerConnection + 服务端信令转发（见 [voice_room.html](zapp/templates/zapp/voice_room.html)）。
- NAT: 自建 STUN Server（见 [stun_server.py](stun_server.py)）。
- 部署: Nginx 反向代理 + Gunicorn/Daphne（见 [SERVER_DEPLOYMENT_GUIDE.md](SERVER_DEPLOYMENT_GUIDE.md)、[README.md](README.md)）。
- 前端: Taro + React + TypeScript + Sass（见 [frontend/package.json](frontend/package.json)）。

## 需求交付流程（MD 驱动）

- (R32) 需求先文档后代码: 拿到任何需求，先生成 `requirements.md` 逐段确认；确认后生成 `design.md` 再确认；确认后生成 `tasks.md` 再确认；确认后才开始写代码。
- (R33) 文档归档目录: 每个需求使用独立目录归档，目录名精确到秒：`YYYY-MM-DD-H点m分s秒-<需求简述>`；该需求的 `requirements.md` / `design.md` / `tasks.md` 必须放在该目录内。
- (R34) HTML 与接口调用: 生成 HTML 页面时，接口调用（请求格式、返回处理、错误处理）优先参照 [timestamp.html](zapp/templates/zapp/timestamp.html) 的 API 调用写法（`fetch` + `response.json()` + `.catch(...)`）。

## 常用命令

- 后端依赖: `python -m pip install -r requirements.txt`
- 本地开发: `python manage.py runserver`
- 测试: `python manage.py test` 或 `python -m unittest`
- 前端依赖: `cd frontend && npm install`
- 前端构建: `cd frontend && npm run build:h5`（或按目标平台选择脚本）

## 项目结构

- [zproject/](zproject/) – Django 项目配置（settings/asgi/urls/wsgi）
- [zapp/](zapp/) – Django App（views/urls/models/services/consumers/templates）
- [zapp/services/](zapp/services/) – 业务服务与可复用逻辑（不直接依赖模板渲染）
- [zapp/templates/zapp/](zapp/templates/zapp/) – 服务端模板与静态交互页面
- [frontend/](frontend/) – Taro 前端工程（React + TS）
- [assets/](assets/) – 静态资源与字体/音频等
- [scripts/](scripts/) – 运维/排障/打包脚本
- [stun_server.py](stun_server.py) – 自建 STUN 服务
- [zpython_django.spec](zpython_django.spec) – PyInstaller 打包配置

## 开发规范

### 代码风格与质量

- (R1) 行数限制: 单文件超过 400 行必须拆分；若因协议/模板必须超限，需要在同目录文档写明原因与拆分困难点。
- (R2) 文档字符串与注释: 对外“契约面”（HTTP API、WebSocket 消息、service 公共方法）必须写清输入/输出/错误；模板中的关键交互点必须标注数据来源与安全假设。
- (R3) 提交前自检: 改动完成后对照本规约自检；若有未满足项，必须显式写入本次变更说明并给出替代措施。
- (R4) 外部契约: 变更以下内容前必须先询问并说明影响范围：
  - HTTP 路由与返回 JSON 结构（`zapp/urls.py`、`zapp/views.py`）
  - WebSocket 事件类型、字段名与时序（`zapp/consumers.py`、前端 `voice_room.html`）
  - 数据库 schema / migration（`zapp/migrations/`、`zapp/models.py` 或 sqlite 表）
  - 前后端约定的请求参数/字段含义（模板/前端调用处）
- (R5) 依赖: 新增/升级 pip 或 npm 依赖前必须说明理由、替代方案与风险并先询问。
- (R6) 分层边界: 视图/消费者只做“协议适配 + 权限校验 + 调用 service”；业务规则与数据处理集中在 `zapp/services/`；禁止在模板/前端代码中复制后端业务规则。
- (R7) 错误模型: 对外接口不得泄露堆栈与内部路径；可预期的校验失败返回稳定的错误码/错误信息；不可预期异常记录日志后返回通用错误。
- (R8) 日志与可观测性: 统一用 `logging`；禁止用 `print` 作为线上日志；日志中禁止出现口令/密钥/会话 token。
- (R9) 文档同步: 对外行为变化（URL、返回字段、页面交互、部署方式）需同步更新 [README.md](README.md) 与本规约。
- (R10) 配置与环境: 禁止把域名/端口/密钥写死在代码里；需要可配置项时优先通过环境变量或 settings 配置集中管理。
- (R11) 资源释放: 文件句柄、子进程、socket、临时文件必须可控释放；能用 `with` 就不用手工 close。
- (R12) 并发模型保护: 修改 Channels 的 async/sync 边界、引入线程/后台任务前必须先询问，并在设计中明确共享状态、锁/队列策略与可观测指标。
- (R13) 命名:
  - Python: 模块/函数/变量 `snake_case`，类 `UpperCamelCase`，常量 `UPPER_SNAKE_CASE`
  - TypeScript/React: 组件 `UpperCamelCase`，变量/函数 `lowerCamelCase`
- (R14) 目录组织:
  - `zapp/views.py` 仅做路由入口与薄逻辑；复杂逻辑下沉到 `zapp/services/`
  - 模板仅负责展示与交互；避免在模板里写“后端同款算法/规则”
- (R15) 上下文管理: I/O、数据库连接、文件操作必须使用上下文管理器或确保异常路径也能释放资源。
- (R16) API 边界: 前端/模板仅调用明确的 HTTP API 或 WS 协议；禁止通过“拼路径/猜字段/依赖隐式副作用”实现联动。
- (R17) 脚本可复现: `scripts/` 下脚本需可重复执行、可输出关键信息；遇到部署/环境问题，优先用脚本固化排查步骤。
- (R18) 可测试性: 新增关键能力需提供最小可自动化验证路径（单元测试、管理命令、自检脚本三选一）。
- (R19) 安全与健壮性: 禁止提交任何密钥/口令/私钥；任何外部输入（GET/POST/JSON/WS 消息）必须做长度/范围/类型校验，并避免 XSS/注入。
- (R20) 静态资源: 字体/音频/图片统一放 `assets/`，并保证路径可在开发与打包环境下工作。
- (R21) 入口约束:
  - HTTP: 入口在 `zapp/urls.py` → `zapp/views.py`
  - WebSocket: 入口在 `zapp/routing.py` → `zapp/consumers.py`
  - STUN: 入口在 [stun_server.py](stun_server.py)
- (R22) 配置 schema: JSON 配置或持久化数据结构新增字段必须给默认值与兼容策略说明。
- (R23) 数据路径: 文件路径拼接必须通过 `os.path.join`；避免硬编码分隔符；Windows/Linux 都应可运行。
- (R24) 代码一致性: 遵循项目既有风格与目录约定；同一模块内保持统一异常处理与返回结构。
- (R25) 前端资源可用: 涉及字体/音频等资源时，必须给出“缺失时的回退策略”和可验证入口（页面/按钮/自检脚本）。
- (R26) 字符串与编码: 所有源码/模板/配置默认 UTF-8；跨前后端传递文本以 UTF-8 处理。
- (R27) 性能: 禁止在 Channels consumer 的 async 路径做阻塞 I/O；需要阻塞操作必须下沉到线程池/任务并明确超时。
- (R28) 状态一致性: 房间/用户/槽位等状态必须有单一事实来源；对外暴露的状态视图必须自洽，避免返回可被外部随意修改的共享引用。
- (R29) 可移植性: 与系统强相关的逻辑（端口探测、进程守护、路径修复）隔离在 `scripts/`；业务逻辑不散落 OS 分支。
- (R30) 代码审查: 影响协议/安全/部署的变更必须双人 Review。
- (R31) 导入规范: 禁止 `from x import *`；避免循环依赖；模块边界处优先显式导入。

### 实时语音（WebRTC + Channels）规范

- 信令协议: 所有 WS 消息必须包含 `type` 字段；新增类型需在后端 consumer 与前端处理处同时落地并更新文档（R4）。
- 房间状态: 房间/槽位的加入离开必须幂等；断线重连需可恢复到一致状态（R28）。
- 超时与清理: 必须定义心跳/超时策略与清理路径；避免僵尸房间长期占用资源（R11）。

## 边界

- ✅ 总是:
  - 改动前后回顾本规约，确保 HTTP/WS 契约与分层边界不被破坏（R4, R6）。
  - 统一编码为 UTF-8，避免敏感信息进入日志与仓库（R19, R26, R8）。
  - 让本地启动与关键功能可复现，必要时更新脚本与文档（R17, R9）。
- ⚠️ 先询问:
  - 变更 URL/返回 JSON/WS 协议字段与时序（R4）。
  - 新增/升级 pip 或 npm 依赖（R5）。
  - 修改异步/并发模型或共享状态策略（R12）。
- 🚫 绝不:
  - 在模板/前端写入密钥、或把敏感信息写进日志（R19, R8）。
  - 让异常堆栈/内部路径作为对外错误返回（R7）。
  - 绕过 service 直接在 view/consumer/模板里堆业务逻辑（R6）。

## 自检清单（提交前）

- 单文件 < 400 行（R1）
- URL/JSON/WS 协议变更已先询问并记录（R4）
- 新增依赖已先询问并说明风险与替代（R5）
- 业务逻辑集中在 `zapp/services/`，view/consumer 仅做薄适配（R6, R21）
- 无敏感信息进入仓库与日志；对外错误不泄露堆栈（R19, R8, R7）
- 新能力具备最小可自动化验证入口（R18）
- README/规约已同步更新（R9）
